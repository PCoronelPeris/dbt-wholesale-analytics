## In one paragraph
The repository now holds a dbt project in the folder `transform/`. It has a hand-written `dbt_project.yml`, a `profiles.yml` with two targets (`dev` and `prod`), and a macro that names schemas as `dev_marts` or `prod_marts`. A `Makefile` gives short commands, and a Python script builds the handbook index from the chapter files. `dbt debug` passes on both targets and `dbt parse` succeeds with zero models.

## 1. The problem this solves
Before this milestone the repository had a Python environment with dbt installed, but no dbt project. dbt cannot run without a project file (`dbt_project.yml`) and a connection file (`profiles.yml`).

Without them, every later milestone would start by fixing the setup instead of building models. Two other gaps would also hurt. Schema names would follow dbt's default rule, which glues the target schema and the custom schema together, so `dev` plus `marts` would become `dev_marts` only by accident of the names chosen. And the handbook index would have to be written by hand, which drifts out of date after the first chapter.

## 3. How it was built
### Step 1 — Open the project and check the starting state
```bash
cd ~/projects/dbt-wholesale-analytics
source .venv/bin/activate
git status
```
`cd` moves the terminal into the repository. `source .venv/bin/activate` puts the virtual environment first on `PATH`, so the word `dbt` runs the copy installed in `.venv/`. `git status` shows what Git sees. The prompt now starts with `(.venv)`.

### Step 2 — Remove leftovers from a first attempt
An earlier run had left a `wholesale_analytics/` folder and a `logs/` folder in the repository root. Before deleting, the command `git ls-files wholesale_analytics logs` was run. Empty output means Git tracks no file there, so `rm -rf` cannot destroy committed work.

### Step 3 — Create the dbt project
```bash
dbt init wholesale_analytics --skip-profile-setup
```
`dbt init` creates a folder with the standard layout. `--skip-profile-setup` stops dbt from asking questions and from writing a `profiles.yml` into the home folder. It also creates a `logs/` folder in the current directory.

### Step 4 — Rename the folder to `transform`
```bash
mv wholesale_analytics transform
```
`mv` renames a folder when the target name does not exist yet. The first try failed twice (E-M01-1 and E-M01-2). The fix was to type the first letters and press Tab, so the shell completes the real name.

### Step 5 — Delete what dbt init generated and we do not want
```bash
rm -rf transform/models/example transform/.gitignore transform/README.md
```
`models/example/` holds two sample models that would run in every build. `transform/.gitignore` and `transform/README.md` duplicate files that live in the repository root (D-M01-2).

### Step 6 — Write `dbt_project.yml` from scratch
The file was written with heredocs (a heredoc feeds the lines up to a closing word into `cat`, which saves them to a file). The final file has 40 lines and 908 bytes.

```yaml
# Project identity
name: wholesale_analytics
version: "1.0.0"
config-version: 2
require-dbt-version: ">=1.11.0,<1.12.0"

# Name of the block in profiles.yml that holds the connection settings
profile: wholesale_analytics

# Folders where dbt looks for each resource type (relative to this file)
model-paths: ["models"]
analysis-paths: ["analyses"]
test-paths: ["tests"]
seed-paths: ["seeds"]
macro-paths: ["macros"]
snapshot-paths: ["snapshots"]

# Folders removed by `dbt clean`
clean-targets:
  - target
  - dbt_packages

# Defaults per folder; a "+" prefix marks a config, not a folder name
models:
  wholesale_analytics:
    staging:
      +materialized: view
      +schema: staging
    intermediate:
      +materialized: ephemeral
      +schema: intermediate
    marts:
      +materialized: table
      +schema: marts

# Project variables (none yet)
vars: {}

# Behavior flags (filled in M16)
flags: {}
```

How to read it:
- `name` is the project name. The `models:` tree must start with this exact name, because dbt matches configs to projects by name.
- `config-version: 2` selects the current file format.
- `require-dbt-version` makes dbt refuse to run on a version outside the range. On a wrong version dbt stops with an error that says the version of dbt is not supported by the project.
- `profile` points to a block of the same name in `profiles.yml`.
- The six `*-paths` lines tell dbt where each resource type lives. They match dbt's defaults, and they are written out on purpose so they can be read and tested.
- `clean-targets` lists folders that `dbt clean` deletes.
- Under `models:`, a key without `+` is a folder and a key with `+` is a config applied to everything in it (D-M01-3).
- `vars: {}` and `flags: {}` are empty on purpose and are filled later.

### Step 7 — Write `profiles.yml` with two targets
```yaml
# Connection settings for the "wholesale_analytics" profile
wholesale_analytics:
  # Output used when --target is not passed
  target: dev
  outputs:
    dev:
      type: duckdb
      path: "{{ env_var('DUCKDB_PATH', '../data/warehouse.duckdb') }}"
      schema: dev
      threads: 4
    prod:
      type: duckdb
      path: "{{ env_var('DUCKDB_PATH', '../data/warehouse.duckdb') }}"
      schema: prod
      threads: 4
```
The file has 15 lines and 420 bytes. `type: duckdb` selects the adapter. `path` uses `env_var`, which reads the environment variable `DUCKDB_PATH` and falls back to the second argument. The fallback is relative to `transform/`, because dbt runs from that folder. `schema` is the default schema of each target. `threads` is how many models dbt may build at the same time. The value contains `{{`, so the whole string is in quotes: a YAML value that starts with `{` without quotes is read as a mapping and fails.

Both targets point to the same database file and differ only in schema. This is deliberate (D-M01-1): DuckDB is a single local file, so environments are separated by schema, not by server.

### Step 8 — Write the schema-name macro
```sql
{# Renders schemas as {target.name}_{custom_schema_name}, for example dev_marts #}
{% macro generate_schema_name(custom_schema_name, node) -%}
    {%- if custom_schema_name is none -%}
        {{ target.schema }}
    {%- else -%}
        {{ target.name }}_{{ custom_schema_name | trim }}
    {%- endif -%}
{%- endmacro %}
```
dbt calls a macro with this exact name every time it decides the schema of a model. Defining it in the project replaces the built-in one. If a model has no custom schema, the target schema is used. If it has one, the result is the target name, an underscore and the custom schema, for example `dev_marts` (D-M01-4). The `-` inside `{%- -%}` removes whitespace, so the schema name has no stray spaces or line breaks. The file has 8 lines and 322 bytes.

### Step 9 — Run `dbt debug` on both targets and `dbt parse`

dbt debug --target dev
dbt debug --target prod
dbt parse

Both `dbt debug` runs ended with `All checks passed!`. The connection block showed `schema: dev` in one and `schema: prod` in the other, and `database: warehouse`: DuckDB names the database after the file, without the extension. `dbt debug` created `data/warehouse.duckdb` with 12,288 bytes and no tables. ### Step 12 — Write the `Makefile`
```make
-include .env
export

VENV := $(CURDIR)/.venv
PYTHON := $(VENV)/bin/python
DBT := $(VENV)/bin/dbt
DBT_DIR := transform

.PHONY: setup build test handbook clean

setup:
	mkdir -p data
	python3 -m venv .venv
	$(PYTHON) -m pip install -r requirements.txt
	cd $(DBT_DIR) && $(DBT) debug --target dev && $(DBT) debug --target prod

build:
	cd $(DBT_DIR) && $(DBT) deps && $(DBT) seed && $(DBT) snapshot && $(DBT) build

test:
	cd $(DBT_DIR) && $(DBT) test

handbook:
	$(PYTHON) scripts/build_handbook_index.py

clean:
	cd $(DBT_DIR) && $(DBT) clean
	rm -f data/*.duckdb data/*.duckdb.wal
```
Every recipe line must start with a TAB character. Pasting a TAB into a terminal triggers autocompletion instead, so the file was written with four spaces and converted with `sed -i 's/^    /\t/' Makefile`. Without the conversion, `make` stops with `missing separator`. The result has 28 lines and 583 bytes. Each recipe line runs in its own shell, so `cd transform && ...` stays on one line (D-M01-5, D-M01-9).

The commands were checked in this order: `make -n setup` and `make -n clean` (the `-n` flag prints the commands without running them), then `make test`, which exited with code 0 and the message `Nothing to do`.

### Step 13 — Write the handbook index script and run it
The folder `scripts/` was created and the file `scripts/build_handbook_index.py` (72 lines, 3,472 bytes) was written in four heredocs, checking the size after each. The script has four parts:
- `section(text, n)` returns the body of the heading `## n. ...` of a chapter.
- `table_rows(block)` returns the rows of the first table in that body, without header lines.
- `meta(text, field)` reads a row such as `| Status | Done |`.
- `main()` reads every file matching `m[0-9][0-9]-*.md`, builds four tables (chapters, errors, decisions, glossary) and writes `docs/handbook/README.md`.

The script is run, never imported, so Python does not create a `__pycache__/` folder (D-M01-10).
```bash
make handbook
```
Output before this chapter existed: `Handbook index: 1 chapters, 6 errors, 8 decisions, 14 terms`. These are the counts of M00.

### Step 14 — Keep the empty `models/` folder in Git
Git stores files, not folders. `transform/models/` was empty after Step 10, so a fresh clone would not contain it. An empty file `transform/models/.gitkeep` was created at close (D-M01-11). The name `.gitkeep` is a convention, not a Git feature.

## 6. Decisions
### D-M01-1 — `profiles.yml` lives in `transform/` and is committed
**Context.** dbt looks for `profiles.yml` in the current folder first and then in `~/.dbt`. **Decision.** Keep the file inside `transform/` and commit it. **Consequences.** The file holds no credentials: the path has a safe default. A clone works without any setup in the home folder. Every dbt command must run from `transform/`, which the Makefile does.

### D-M01-2 — Delete `transform/.gitignore` and `transform/README.md`
**Context.** `dbt init` writes both files. **Decision.** Delete them. **Consequences.** The root `.gitignore` is the only ignore file and the root `README.md` is the only README.

### D-M01-3 — Materializations by layer
**Context.** Each folder needs a default materialization (how dbt stores a model). **Decision.** Staging is `view`, intermediate is `ephemeral`, marts are `table`. **Consequences.** An intermediate model creates nothing in the warehouse unless a model overrides the default. M05 must override it if an intermediate model needs to be inspected as a table.

### D-M01-4 — The macro uses `target.name`, with a fallback to `target.schema`
**Context.** dbt's built-in rule joins the target schema and the custom schema. **Decision.** Join the target name and the custom schema, and use the target schema when there is no custom schema. **Consequences.** Schemas read `dev_staging`, `prod_marts` and so on. A future `bq` target must be named so that its prefix is acceptable as a BigQuery dataset name.

### D-M01-5 — The Makefile calls `.venv/bin/*` by absolute path
**Context.** A `make` command should not depend on whether the environment is activated. **Decision.** Define `VENV`, `PYTHON` and `DBT` from `$(CURDIR)` and use them in every recipe. **Consequences.** `make test` works from a fresh terminal. Running `dbt` by hand still needs `source .venv/bin/activate`.

### D-M01-6 — Names are completed with Tab
**Context.** Two errors (E-M01-1 and E-M01-2) came from names typed by hand. **Decision.** Press Tab to complete folder and file names. **Consequences.** Fewer typos. If Tab completes nothing, the name does not exist.

### D-M01-7 — Files are created from the terminal with heredocs
**Context.** No editor for files inside WSL has been chosen yet. **Decision.** Create files with `cat > file <<'EOF'` and check size with `wc -l -c`. **Consequences.** Every file is reproducible from the commands. The editor choice stays open.

### D-M01-8 — `.user.yml` is added to `.gitignore`
**Context.** The milestone listed three lines for `.gitignore`. dbt also writes `transform/.user.yml`, a 41-byte file with an anonymous identifier. **Decision.** Add a fourth line, `.user.yml`. **Consequences.** The file is never committed. This deviates from the milestone text.

### D-M01-9 — `make clean` also removes the `.wal` file, and `make setup` does not upgrade pip
**Context.** DuckDB can leave a `.duckdb.wal` file (its write-ahead log) next to the database. Upgrading pip would change the installed version outside `requirements.txt`. **Decision.** `clean` deletes `data/*.duckdb.wal` as well, and `setup` installs only the pinned requirements. **Consequences.** A clean state is really clean, and installs are reproducible. The brief's Makefile table changes by one line.

### D-M01-10 — The index script is run, not imported, and is not compiled in advance
**Context.** Python writes a `__pycache__/` folder when a file is imported or compiled. The `.gitignore` does not list it. **Decision.** Run the script directly with `make handbook` and skip `python -m py_compile`. **Consequences.** No `__pycache__/` appears. If a later script is imported by another, `__pycache__/` must be added to `.gitignore` first.

### D-M01-11 — `transform/models/.gitkeep` is added
**Context.** The milestone does not mention it, but Git does not store empty folders. **Decision.** Create an empty `.gitkeep` in `models/`. **Consequences.** A fresh clone has the full folder layout. The file is removed or left in place when real models arrive, at no cost either way.

## 8. New terms
| Term | Meaning |
|---|---|
| dbt project | A folder that contains a `dbt_project.yml` file; dbt finds it in the current folder or in a parent folder, never in a subfolder |
| `dbt_project.yml` | The file that names a dbt project and sets its folder paths, defaults and version limits |
| `profiles.yml` | The file that holds connection settings; dbt reads it from the current folder first and then from `~/.dbt` |
| Profile | A named block in `profiles.yml`; the project picks one with the `profile` key |
| Target | One named connection setting inside a profile, such as `dev` or `prod`, chosen with `--target` |
| Threads | The number of models dbt may build at the same time on a target |
| Materialization | The way dbt stores a model in the warehouse: view, table, ephemeral, incremental and others |
| Custom schema | A schema set with `+schema` on a model or folder, which dbt combines with the target through `generate_schema_name` |
| Macro | A reusable block of Jinja code, written in a `.sql` file inside `macros/` |
| Jinja | The templating language dbt uses; `{{ }}` prints a value and `{% %}` runs logic |
| `generate_schema_name` | The macro dbt calls to decide the schema of every model; defining it in a project replaces the built-in one |
| `require-dbt-version` | A `dbt_project.yml` key that limits which dbt versions may run the project |
| `env_var` | A Jinja function that reads an environment variable and accepts a default value |
| YAML | A text format of keys and values where indentation, made only of spaces, shows nesting |
| Partial parsing | dbt reuses the saved result of the last parse and re-reads only what changed; a change of target or profile forces a full parse |
| Makefile | A file named `Makefile` with named recipes that the program `make` runs |
| Make target | The name before the colon in a Makefile, such as `test`; `make test` runs its recipe |
| `.PHONY` | A Makefile line that tells make a target is a recipe name and not a file |
| Dry run | A run that prints the commands without executing them; `make -n` does this |
| Exit code | The number a command returns when it ends; 0 means success and any other number means failure |
| `.gitkeep` | An empty file, by convention, that lets Git keep a folder that would otherwise be empty |
| Regular expression | A pattern that describes text to find, used by the index script to locate headings and IDs |

## 9. Check yourself
<details><summary>Q1. A model sets `{{ config(materialized='view') }}` in its SQL file. The folder default in `dbt_project.yml` is `+materialized: table`. Which one applies, and why?</summary>

The view applies. dbt applies the most specific config: a `config()` block in the model file beats a properties YAML file, which beats `dbt_project.yml`. The tempting answer is that the project file wins because it is the central file, but it is the lowest priority of the three.

</details>

<details><summary>Q2. The project has `require-dbt-version: ">=1.11.0,<1.12.0"` and a teammate runs dbt 1.12.0. What happens?</summary>

dbt stops before doing any work and reports that this version of dbt is not supported by the project. The flag `--no-version-check` skips the check. The tempting answer is that dbt only prints a warning and continues; it does not, because the key is a hard limit.

</details>

<details><summary>Q3. The target is `dev` with `schema: analytics_dev`. A model has `+schema: marts`, and the project uses dbt's built-in `generate_schema_name`. In which schema is it built?</summary>

In `analytics_dev_marts`. The built-in macro joins the target schema and the custom schema with an underscore; it does not replace the target schema. The tempting answer is `marts`, which would be true only with a macro that returns the custom schema alone. This project overrides the macro so that the prefix is the target name, so the same model would build in `dev_marts`.

</details>
